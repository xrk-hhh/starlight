体检自己的网站时，我遇到了一件很尴尬的事：**线上一切正常，本地预览却整页白屏**。更尴尬的是，我一度以为是自己刚改的代码把站点改坏了。最后查清真相，三个现象背后其实只有一条教训：**现象不等于证据，先分清它是代码说的，还是环境说的**。

这篇文章记下这三个假象，以及现在我用来区分它们的方法。

## 假象一：本地预览白屏，其实是浏览器和服务器没握上手

症状很唬人：本地打开预览页，导航和页脚渲染出来了（那是写死在 HTML 壳里的），正文区域全空，控制台安安静静，一个报错都没有。

第一反应当然是「我改坏了代码」。但真正的入口在于一个容易被忽略的细节：**本地预览没起来，和站点起坏了，看起来是一模一样的**。我打开控制台看脚本标签，发现引用的资源请求全都返回了 **200**。

200 就是好消息吗？不是。我看了响应的 `Content-Type`——返回的是 `text/html`。也就是说，浏览器请求 `assets/index-xxxx.js`，服务器给了它一整页 HTML。浏览器拿到一段以 `<!doctype html>` 开头的「JavaScript」，自然一个字都执行不了；而这类解析失败不会在页面里留下红字，只会安静地什么都不发生。

再把本地到服务器的链路拆开看，三件事叠在了一起：

- 预览服务器**只监听了 IPv6 的回环地址**，而浏览器默认先解析 IPv4 的 `localhost`——请求打到了一个没有服务的地方；
- 剩下的请求落在服务器的 **SPA 回退分支**上：一个只服务单页应用的静态服务器，会对「没找到的文件」返回 `index.html`，好让前端路由接管——于是 JS 请求也被顶替成了 HTML；
- 项目部署在子路径下（`/starlight/`），路径前缀又给排查加了一层噪音。

三条任意一条单独出现都不难查，叠在一起就变成了「代码坏了」的错觉。

![静态资源被 SPA 回退顶替的请求链路](/starlight/images/blog/preview-mime.svg)

**现在的做法**：本地验收走一个明确的静态服务器，只服务构建产物、不做回退猜测，并且**校验响应的 MIME 类型**——脚本请求必须拿到 JavaScript，样式请求必须拿到 CSS，否则就是环境问题，不要去看业务代码。

## 假象二：构建门说「通过」，不等于类型真的检查过了

第二个假象来自一次刻意设计的探针：往数据文件里写入一个不存在的字段，再跑 `npm run build`——**退出码 0，构建成功**。

明明构建脚本的第一步就是类型检查。原因在于它用的是带增量构建的类型检查模式：它依赖一份构建信息缓存来判断「哪些文件需要重新检查」。如果被检查文件的**集合本身**发生了变化，缓存里的结论就可能不再成立，而这一步依然安静地通过。换句话说，构建门在「通过」，但它检查的很可能是它以为的那批文件。

**现在的做法**：验收时直接用一次性的全量检查命令（`vue-tsc -p tsconfig.app.json --noEmit`），让每次判断都从零开始；日常开发再享受增量缓存的速度。**快的那条留给开发，准的那条留给验收**。

## 假象三：同一个地址，在不同机器上不是同一个东西

排查中最费时间的一步，是意识到「我看到的」和「访问者看到的」可能不是一回事：

- `localhost` 在有的环境解析到 IPv6 回环，在有的环境是 IPv4；
- 部署在子路径下，任何一条**写死根路径**的资源引用都会在预览里 404，而线上却恰好能命中；
- 浏览器缓存会让你看到上一个版本的资产，尤其在反复构建同一个产物路径的时候。

这三条都不是代码 bug，但它们制造的现场和 bug 一模一样。

## 一条通用纪律：先造一个自己能控制的现场

回头看，这三个假象能被快速定性，靠的都是同一类动作——**换一个我能完全控制的最小现场**：

- 不确定服务器行为？直接用 Node 内置模块发一个原始请求，打印状态码、响应头和前几十个字节，而不是猜；
- 不确定是不是缓存？给它一个永不缓存的响应头，或者换个地址重开；
- 不确定是不是路由栈的问题？直接请求资源本身，绕过前端路由再看一次。

结论很简单：**先问「这个现象是谁产生的」，再问「我的代码哪里错了」**。这次的答案全是前者——我改的代码一行都没问题，问题出在我用来观察它的工具上。

而这也是为什么要给工具本身写测试：一个会说谎的观测工具，会让你花一整天去修一个根本不存在的 bug。
